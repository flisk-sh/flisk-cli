# Adopt Flisk next to an existing Docker Compose file

For a repository that already has a root `docker-compose.yml` and wants `flisk up` as a second way to start the stack, without giving up plain `docker compose`. Written from the same four real adoptions that shaped the importer and exporter: [TubeHaus](https://github.com/biolend83/tubehaus), [dilolabs/nosia](https://github.com/dilolabs/nosia), [Lychee](https://github.com/LycheeOrg/Lychee) and [pl_mail](https://github.com/karatektus/pl_mail). What each one needed is tracked in [ADOPTER-COVERAGE.md](../project/ADOPTER-COVERAGE.md).

## 1. Import the Compose file

`flisk import` reads one file, the root `docker-compose.yml`, and writes one bring-your-own `service.json` per Compose service, plus `.flisk/project.json` when the directory is not a Flisk project yet. It does not read other Compose file names, override files, Dockerfiles, `package.json` or Procfiles, and it names what it did not translate.

```bash
flisk import . --dry-run   # print the plan, write nothing
flisk import . --yes       # write the service.json files
```

The importer covers the common Compose surface: `image` (including `${VAR}` tags), `build`, `ports` (with the host bind address), `volumes` (including named volumes, which keep their Docker name so existing data is reused), `environment`, `env_file`, `healthcheck`, `depends_on` conditions, `profiles`, `restart: on-failure:N`, `stop_grace_period`, `tmpfs`, `deploy` limits, `models` and `networks` aliases. Anything it cannot express is reported instead of silently dropped; [ADOPTER-COVERAGE.md](../project/ADOPTER-COVERAGE.md) lists every feature and its status.

Commit the `service.json` files with the services they describe. `service.json` becomes the source of truth; Compose stays available because it is generated, not because it is still authored by hand.

## 2. Keep a standalone Compose file in `.autogenerated/`

`flisk export compose` writes a standalone `docker-compose.yml` from the bring-your-own `service.json` files into `.autogenerated/`, committed and marked do-not-edit:

```bash
flisk export compose
docker compose --env-file .env -f .autogenerated/docker-compose.yml up -d
```

That file runs without Flisk, so teammates and CI jobs that do not use `flisk up` keep working. It is never deploy config: `flisk export` writes files only and calls no cloud API. Do not edit `.autogenerated/` by hand; change `service.json` and export again.

## 3. Keep both in step in CI

Two checks catch drift:

- `flisk export compose --check` exits 1 when `.autogenerated/docker-compose.yml` differs from what the `service.json` files would produce. Run it in CI so a `service.json` edit without a re-export fails the build.
- `flisk config verify` exits 1 when a file under `.flisk/.flisk-out/` was edited by hand or is stale relative to `.flisk/project.json`.

```bash
flisk export compose --check
flisk config verify
```

## 4. The `.env` that Compose expects

Plain `docker compose -f .autogenerated/docker-compose.yml up` reads `.env` from the compose file's own directory, `.autogenerated/`, which is not where the project's values live. The generated file's header therefore tells you to pass the project `.env` explicitly:

```bash
docker compose --env-file .env -f .autogenerated/docker-compose.yml up -d
```

`.env` means the project root `.env`, the gitignored file that holds real values, not a committed `.env.example` full of placeholders. The importer never copies values out of the Compose file: put the environment values the services need in the project `.env`. `${VAR}` and `${VAR:-default}` in `service.json` fields (image tags, `extraPorts`, `models`, `extraHosts`) resolve from the shell and that project `.env`, and a required secret is written as `${NAME:?NAME is not set, add it to .env}` so Compose fails fast with a clear message instead of starting with an empty value.

## 5. When an image has no `curl`

A Compose `healthcheck` that runs `curl` or `wget` fails on an image that does not ship the tool (`executable file not found`). The container then reports `unhealthy` no matter how well the app works, which is what Lychee's facial-recognition sidecar hit. The fix is to probe something the image actually has:

- `healthCheck.port`: ready when a TCP port accepts a connection. The generated probe tries `nc`, then bash's `/dev/tcp`, then `bun`/`node`, in that order, so most images already have one of them.
- `healthCheck.command`: ready when the command exits 0, run inside the container, for example `["grpc_health_probe", "-addr=:9090"]`. Pick a binary the image ships.
- `healthCheck.path`: the default HTTP probe. Use it only when the image can answer HTTP and has a tool to check it.
- `healthCheck: false`: no container health check at all, matching `healthcheck: disable` in Compose.

Flisk also does not let a probe that never ran speak for the app: a check whose command could not execute (exit 127 with `not found`, or `OCI runtime exec failed` for the exec form) proceeds with a warning rather than reporting the app down. A probe that runs and fails still blocks dependents. See [service.json](../service-json.md#dependencies-routes-and-health-checks) for the full `healthCheck` contract.

## 6. Models (Compose `models`, Docker Model Runner)

A Compose file such as nosia's asks Docker Model Runner for its models with a top-level `models:` block. `flisk import` carries it into `service.json` as `models`, a list of `{ "name", "model" }` per service, and `flisk export compose` writes it back out:

```json
"models": [
  { "name": "llm", "model": "${LLM_MODEL:-ai/smollm2}" }
]
```

`models` applies to bring-your-own resources only, and starting the container needs Docker Model Runner enabled in Docker Desktop or the `docker-model-plugin` installed. `flisk doctor` and `flisk up` warn when a service declares models but `docker model version` fails, instead of leaving you with Compose's `'models' support requires Docker Model plugin` message. Details and the validation rules are in [byo.md](../byo.md#models-compose-models-docker-model-runner).

## 7. Check it on Linux: a GitHub Actions job

The fastest way to know the imported stack is honest is a throwaway job that boots it on a clean Linux machine, the same shape used for the nosia and Lychee checks. `ubuntu-latest` comes with Docker; Tilt and Flisk are installed in two steps. Save it as `.github/workflows/flisk-up.yml`:

```yaml
name: flisk up

on:
  pull_request:
  workflow_dispatch:

permissions:
  contents: read

jobs:
  boot:
    runs-on: ubuntu-latest
    timeout-minutes: 30
    env:
      FLISK_VERSION: "1.4.73"   # the version the project was adopted on
      FLISK_STACK: shop         # the stack flisk up should start
    steps:
      - uses: actions/checkout@v7
        with:
          persist-credentials: false

      - uses: actions/setup-node@v7
        with:
          node-version: 22

      # The runner image has Docker; Tilt is not preinstalled.
      - name: Install Tilt
        run: curl -fsSL https://raw.githubusercontent.com/tilt-dev/tilt/master/scripts/install.sh | bash

      # ubuntu-latest runs a preinstalled Postgres on 5432; stop it so the
      # stack's own Postgres can bind the port.
      - name: Free port 5432
        run: |
          if ! sudo ss -ltn 2>/dev/null | grep -q ':5432 '; then
            echo "port 5432 is free"; exit 0
          fi
          sudo systemctl stop postgresql.socket 'postgresql@*.socket' postgresql.service 'postgresql@*.service' 2>/dev/null || true
          sudo systemctl mask postgresql.service postgresql.socket 2>/dev/null || true
          sudo fuser -k 5432/tcp 2>/dev/null || true

      - name: Install flisk
        run: |
          npm install --global "@flisk-sh/flisk@${FLISK_VERSION}"
          flisk --version

      # A fresh clone has no git-ignored .env; create one from the example the
      # project documents, or write the secrets the job needs first.
      - name: Prepare .env
        run: test -f .env || cp .env.example .env 2>/dev/null || touch .env

      - name: Start the stack and wait for health
        run: flisk up "$FLISK_STACK" --wait --wait-timeout 900

      # `if: always()` so the evidence is there on a red run, when it matters.
      - name: Collect docker ps and container logs
        if: always()
        run: |
          mkdir -p "$RUNNER_TEMP/flisk-evidence"
          docker ps -a --format 'table {{.Names}}\t{{.Status}}\t{{.Ports}}' > "$RUNNER_TEMP/flisk-evidence/docker-ps.txt" 2>&1 || true
          for c in $(docker ps -aq); do
            docker logs --tail 300 "$c" > "$RUNNER_TEMP/flisk-evidence/${c}.log" 2>&1 || true
          done

      - name: Upload container state and logs
        if: always()
        uses: actions/upload-artifact@v4
        with:
          name: flisk-up-${{ github.run_id }}
          path: ${{ runner.temp }}/flisk-evidence/
```

Two details worth keeping:

- `flisk up <stack> --wait` starts the stack in the background and returns 0 once every service is healthy, 1 on failure or when `--wait-timeout` passes. The stack keeps running, so the evidence step afterwards still finds containers up.
- The evidence step order matters less than `if: always()`: run it whether `flisk up` passed or failed, and read the artifact when a `container is running, but its health check is failing` line is all the log shows (a check such as `docker inspect <container> --format '{{json .State.Health}}'` shows the probe command and its last output).

A longer two-job variant that also runs `flisk config verify` and polls each printed health URL is in [Running Flisk in CI](../ci.md).

## What this does not cover

`flisk up` is a local development environment, not a deployment path, and the generated Compose file is a convenience for people without Flisk, not a production manifest; see [scope.md](../scope.md). Production stays on whatever the repository already uses. If the import names a feature as untranslated, that is a Flisk gap: file it rather than working around it in your repository, as [ADOPTER-COVERAGE.md](../project/ADOPTER-COVERAGE.md) explains.
